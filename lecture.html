01

なぜCAD→ゲームアセット変換が必要か背景・動機・設計思想

この章のポイント

「何を作るか」より「なぜ作るか」を先に理解することで、設計判断の理由がわかる。

ゲーム開発における手作業のコスト

建築・乗り物・設備を扱うゲームタイトルでは、設計図面が先に存在することが多い。 しかし CAD ソフト（AutoCAD等）の出力と、Unity/Unreal が読めるフォーマットは異なる。 その「翻訳」を手作業でやっているスタジオが今もある。

従来の手作業フロー vs 自動化フロー
BEFORE（手作業）
設計者がDXFを作成
↓
モデラーが手動で3D化（数日〜数週間）
↓
エンジニアがUnityに取り込み
↓
修正が入るたびに繰り返し
→
AFTER（自動化）
設計者がDXFを作成
↓
cli.py run building.dxf（〜10秒）
↓
Unity/UEにインポート可能なOBJ

このパイプラインが解く問題

  • 形式の不一致：DXF は CAD 専用、OBJ/GLB はゲームエンジン向け
  • 3D情報の不足：建築平面図は2Dなので、高さ情報をアルゴリズムで補完する必要がある
  • 逆変換の需要：ゲームアセットから設計図面を逆生成したいケースも存在する
設計方針

「完璧なAI推論」より「正確なアルゴリズム」を優先した。 TripoSRなどの汎用推論モデルは建築物に対して学習分布とのズレが大きく、 ゲームアセットとしての実用性は押し出しメッシュの方が高いと判断した。

DXFファイルの構造とルート自動判定パーサ設計・条件分岐

DXF（Drawing Exchange Format）とは

AutoDesktopが1982年に策定したCADデータ交換フォーマット。 テキスト形式（ASCII）でエンティティ（直線・ポリライン・テキスト等）を列挙する。 グループコードと呼ばれる数値タグで型を識別する。 

DXF (抜粋)
  0        ← グループコード 0 = エンティティ型
LINE       ← 直線
  8        ← グループコード 8 = レイヤー名
壁1階      ← CP932エンコードされたレイヤー名
 10        ← X座標 (始点)
100.0

POLYFACE フラグの判定

Python
def _has_polyface(msp) -> bool:
    # DXFのPOLYLINEエンティティを走査
    for e in msp:
        if e.dxftype() == "POLYLINE":
            # flags の 0x40 ビットが立っている = 3D POLYFACE メッシュ
            if e.dxf.get("flags", 0) & 0x40:
                # Z値が0でない頂点があれば本物の3Dメッシュ
                z_vals = [v.dxf.location.z for v in list(e.vertices)[:20]]
                if max(abs(z) for z in z_vals) > 1e-6:
                    return True
    return False

なぜフラグのビット判定に & 0x40（AND演算）を使うのか？
flags は複数の状態を1つの整数で表現している（ビットフラグ）。0x40 = 64 = 0b01000000 のビットだけを抽出するため。

Zバッファによる隠線判定アルゴリズムラスタライズ・バリセントリック座標

この章の核心

GPUが毎フレーム行っていることを、numpy だけで再実装する。リアルタイムグラフィックスの根幹を理解する最良の演習。

問題設定：どのエッジが「見える」か

3DモデルをCAD図面（三面図）に変換するとき、すべてのエッジを描くと内部の線まで見えてしまう。 「手前にあって見えるエッジ（実線）」と「奥にあって隠れているエッジ（破線）」を区別する必要がある。

手法アイデア問題点VISIBLE比率
v1: 深度中央値エッジ深度の中央値より奥=隠線メッシュ形状を無視した分類0.1%
v2: 法線ベース面法線が手前を向く=前面曲面・自己遮蔽を扱えない27.7%
v3: Zバッファ深度マップと比較（現行・最善）78.0%

Step 1：バリセントリック座標法で三角形をラスタライズ

三角形の内部にあるピクセルを判定し、深度値を補間して書き込む処理。 これがZバッファ生成の中核。

w₀ = [(h₁-h₂)(gx-h₂) + (v₂-v₁)(gy-v₂)] / area
w₁ = [(h₂-h₀)(gx-h₀) + (v₀-v₂)(gy-v₀)] / area
w₂ = 1 - w₀ - w₁

ピクセル(gx,gy)が三角形内部 ⟺ w₀≥0 ∧ w₁≥0 ∧ w₂≥0
深度値 = w₀·d₀ + w₁·d₁ + w₂·d₂ 
Python (numpy)
def _build_zbuffer(verts, faces, ax_h, ax_v, ax_d, size=512):
    z_buf = np.full((size, size), np.inf, dtype=np.float32)
    
    for face in faces:
        a, b, c = face
        h0, h1, h2 = px_h[a], px_h[b], px_h[c]  # ピクセル座標
        v0, v1, v2 = px_v[a], px_v[b], px_v[c]
        d0, d1, d2 = pts_d[a], pts_d[b], pts_d[c]  # 深度値
        
        # バウンディングボックス（処理範囲を絞る）
        xmin, xmax = max(0, int(min(h0,h1,h2))), min(size-1, int(max(h0,h1,h2))+1)
        ymin, ymax = max(0, int(min(v0,v1,v2))), min(size-1, int(max(v0,v1,v2))+1)
        
        # グリッド生成 → バリセントリック座標を一括計算
        gx, gy = np.meshgrid(np.arange(xmin, xmax), np.arange(ymin, ymax))
        area = (h1-h0)*(v2-v0) - (h2-h0)*(v1-v0)
        if abs(area) < 0.5: continue
        
        w0 = ((h1-h2)*(gx-h2) + (v2-v1)*(gy-v2)) / area
        w1 = ((h2-h0)*(gx-h0) + (v0-v2)*(gy-v0)) / area
        w2 = 1.0 - w0 - w1
        inside = (w0 >= -0.01) & (w1 >= -0.01) & (w2 >= -0.01)
        
        # 深度補間 → Zバッファに書き込み（手前のみ更新）
        depth = w0*d0 + w1*d1 + w2*d2
        z_buf[gy[inside], gx[inside]] = np.minimum(
            z_buf[gy[inside], gx[inside]], depth[inside]
        )
    return z_buf

Step 2：エッジの可視性判定

生成した深度マップを使って、各エッジが「手前にあるか」を判定する。 1点だと誤判定が多いので5点サンプリングして多数決を取る。 

Python
def _edge_visibility_zbuffer(x0, y0, x1, y1, d0, d1, z_buf, params, n_samples=5):
    visible_votes = 0
    
    for t in np.linspace(0.1, 0.9, n_samples):
        # エッジをt:1-tで分割した点の座標・深度
        mx, my = x0 + t*(x1-x0), y0 + t*(y1-y0)
        md = d0 + t*(d1-d0)
        
        # ピクセル座標に変換してZバッファを参照
        px = int(np.clip(mx * scale_h + off_h, 0, size-1))
        py = int(np.clip((1.0 - (my*scale_v+off_v)/size) * size, 0, size-1))
        
        zbuf_depth = z_buf[py, px]
        # エッジの深度 ≤ Zバッファの深度 + 許容誤差 → 可視
        if zbuf_depth == np.inf or md <= zbuf_depth + tol:
            visible_votes += 1
    
    return "visible" if visible_votes > n_samples // 2 else "hidden"

なぜ t=0 と t=1（端点）ではなく t=0.1〜0.9 でサンプリングするのか？
端点はちょうど別の面の境界に乗ることがあり、誤判定しやすい。中間点を使うことで安定する。

性能について

現実装は三角形ごとにforループを回すためcar.dxf（14,234面）で約0.8秒かかる。 numpy のnp.frompyfuncやnumbaを使えば10〜100倍高速化できる。 ゲームエンジンのレンダラはこれをGPUで毎秒60回以上やっている。

文字コードの罠：CP932 Mojibake問題エンコーディング・バイト列操作

注意

日本語を扱うシステムでは文字コードの問題が必ず出てくる。 この問題を解決した手法は他の日本語CADデータ処理でも応用できる。

問題の構造

日本語CADソフトはレイヤー名を CP932（Shift_JIS） でDXFに書き込む。
しかし ezdxf（PythonのDXFライブラリ）は内部で cp1252（Windows西欧語）として読み込む。
この不一致が Mojibake（文字化け） を引き起こす。

「壁」という文字が化ける仕組み
「壁」 → CP932エンコード → 0x95 0xC7
↓ ezdxf が cp1252 として読む
0x95 → cp1252 の '•'（U+2022 BULLET）
0xC7 → cp1252 の 'Ç'（U+00C7）
結果: ezdxf 内部では "•Ç1階" として保持される

解決策：Mojibakeパターンを事前生成してマッチング

「壁」などのキーワードを CP932→cp1252 変換した文字列 として保持しておき、 ezdxf が返す化けた文字列と直接比較する。 

Python
def _cp932_moj(text: str) -> str:
    """CP932テキスト → ezdxf内部のcp1252 Mojibake文字列に変換"""
    b = text.encode("cp932")          # バイト列に変換
    result = []
    for byte in b:
        if 0x80 <= byte <= 0xFF:       # 非ASCII領域
            try:
                result.append(bytes([byte]).decode("cp1252"))
            except ValueError:
                # cp1252 未定義バイト(0x81等)はsurrogate文字に
                result.append(chr(0xDC00 + byte))
        else:
            result.append(chr(byte))
    return "".join(result)

# 壁 → "•Ç" というMojibakeパターンを保持
_WALL_MOJ = [_cp932_moj("壁")]    # → "•Ç"

# マッチング：ezdxfのraw文字列に含まれているか確認
def _raw_match(raw: str, patterns: list) -> bool:
    return any(p and p in raw for p in patterns)

建築平面図の押し出し改善5項目Union-Find・幾何演算・複数階積み上げ

① 端点スナップ：Union-Find アルゴリズム

建築CADの壁線分は接合点が数mm〜数十mmずれていることが多い。 そのまま押し出すと壁に隙間や浮きが生じる。 Union-Find で近接端点をグループ化して統合する。 

Union-Find の核心部分
# 全端点を配列として用意
pts = np.array([[s[0],s[1]] for s in segs] + [[s[2],s[3]] for s in segs])
parent = list(range(len(pts)))

def find(x):           # パス圧縮付きfind
    while parent[x] != x:
        parent[x] = parent[parent[x]]
        x = parent[x]
    return x

# 80mm以内のペアを結合
for i in range(len(pts)):
    for j in range(i+1, len(pts)):
        if np.hypot(pts[i,0]-pts[j,0], pts[i,1]-pts[j,1]) < 80.0:
            union(i, j)

② 壁厚自動推定：平行線ペア検出

建築CADでは壁を2本の平行線で表現する慣習がある。 この性質を利用して実際の壁厚を推定する。

③ 開口部の高さ分類

建具（ドア・窓）を線分長さで分類し、それぞれ適切な高さで壁を切り抜く。

種別判定条件切り抜き高さ

窓線分長 < 900mm900mm 〜 2000mm

④ 複数階の積み上げ

レイヤー名から1階/2階を検出して、別々のZ座標に配置する。

2階建て住宅の積み上げ構造
天井スラブ Z=5.5〜5.65m
壁2階（97本） Z=3.0〜5.5m
天井スラブ Z=2.5〜2.65m
壁1階（61本） Z=0〜2.5m
床スラブ Z=-0.2〜0m

⑤ 天井スラブ

各階の天井に150mm厚のスラブを追加することで、建物としてのリアリティを向上させる。

設計上のトレードオフ

ブーリアン Union（--use-union）を有効にすると壁同士の重なりが解消されてきれいになるが、 処理時間が大幅に増加する。デフォルトは無効にして concatanate（単純結合）を使っている。 ゲームアセットとしては多少の重なりがあっても実用上問題ないという判断。

GPU推論パイプラインの設計と限界TripoSR・Zero123++・TSDF Fusion

重要な設計判断

この章では「試みて失敗した方法」と「なぜ方針を変えたか」を詳しく説明する。 技術選択の判断プロセスはエンジニアとして最も重要なスキル。

当初のアプローチ：Zero123++ + TSDF Fusion

押し出しメッシュ
→
レンダリング
→
Zero123++6視点生成
→
深度推定
→
TSDF Fusion❌失敗

失敗の原因：TSDF Fusion はカメラ姿勢（外部パラメータ）が正確でないと 正しいメッシュを再構成できない。Zero123++ が出力する6視点の画像と、 TSDF に渡すカメラ行列が一致していなかった。結果は花びら状のノイズ。

TripoSR への切り替え

TSDF を完全に廃止し、単視点画像から直接メッシュを出力する TripoSR を採用。 Transformer ベースで中間表現を経由せずメッシュを生成するため、 カメラ姿勢問題は原理的に発生しない。

モデル仕組み建物への適性VRAM
Zero123++ + TSDF多視点生成→点群再構成❌ カメラ姿勢問題8GB
TripoSR単視点→直接メッシュ△ 学習分布のズレ6GB
押し出し（現行）アルゴリズム処理✅ 寸法精度100%不使用

学習分布のズレという根本問題

TripoSR・Zero123++ はどちらも「自然物・製品の写真」で学習されている。 建築平面図から生成したシルエット画像は、学習データとは大きくかけ離れており、 どんな高品質モデルでも期待通りの出力は得にくい。

建築特化モデルの現状調査
  • HouseCrafter（2024）：最高品質だがコード非公開
  • Plan2Scene（2021・CVPR）：写真も必要でDXF単体入力に非対応
  • FloorPlanTo3D：品質が押し出し改善版と大差なし

→ 「汎用推論モデル」より「ドメイン特化アルゴリズム」の方がゲームアセットとして価値が高いと判断。

実務での設計判断：3つの原則

原則1: 測ってから判断する

「たぶん改善した」ではなく数字を出す。隠線判定は 0.1% → 27.7% → 78% と段階的に改善を追跡した。

原則2: フォールバックを用意する

新機能（ブーリアン Union、推論）が失敗しても基本機能（concatenate、押し出しのみ）で動き続けるようにする。

原則3: 技術より目的を優先する

「最新のAIモデルを使うこと」が目的ではない。「ゲームアセットとして使える品質」が目的。アルゴリズムの方が目的に合致するなら迷わずそちらを選ぶ。
