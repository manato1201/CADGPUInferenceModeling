# 6. トラブルと保守

## 症状 → 原因 → 直し方

| 症状 | 原因 | 直し方 |
|---|---|---|
| `DXF file not found` | パスが違う | 絶対パスで渡す |
| `is not a DXF file`(API で `input_error`) | DXF でない(先頭の `0 / SECTION` が無い)・DWG | DXF に書き出し直す(**DWG は、読めない**) |
| 壁の間に隙間・閉じない | 端点が許容距離より離れている | `wall_snap_tol` を大きく(大きすぎると連鎖する) |
| 壁が太すぎる・細すぎる | 壁厚の自動推定が外れた | `auto_wall_thickness` を切り、`wall_thickness` を指定 |
| 寸法線が壁になる | 「壁寸法」が壁に分類される(**既知の問題 3**) | レイヤー名を直す・分類の順序を直す |
| 日本語のレイヤーが分類されない | 文字化けの形が違う(CP932 でない) | `_cp932_moj` の元の語・文字コードを確かめる |
| CUDA の OOM(`inference_error`) | VRAM が足りない(8GB 級) | 画像サイズ・ビューの数を減らす。TripoSR(軽い)を使う |
| API の変換が終わらない | 時間切れの後も、**スレッドは動き続ける**(強制終了できない) | プロセスごと再起動。長い処理は、別プロセスに分ける |
| 作業フォルダが増える | ジョブの TTL・上限(1 時間・500 件)の掃除は、**新しい変換のときだけ**走る | 手で `WORK_DIR` を整理 |
| Z バッファの初回が遅い | `numba` のコンパイル | 2 回目から速い(`cache=True`) |

## 既知の問題(コードは変えていない。直すときの手がかり)

講義・学習資料の作成中に、コードを読んで・動かして見つけたものです。

### 1. `POST /convert` が、クライアントのファイル名を、そのままパスに使う

`dxf_path = job_dir / file.filename`。`UploadFile.filename` は**クライアントが決める文字列**で、`..\..\x.dxf` のような値だと、作業フォルダの**外に書き込める**可能性がある(拡張子の確認は `.dxf` / `.dwg` だけ)。**直す案**: `Path(file.filename).name` だけを使う・固定の名前(`input.dxf`)に保存する。

### 2. API は、認証も、アップロードの大きさの上限も無い

`await file.read()` で全体をメモリに読む。公開すると、誰でも変換を投げられ、GPU を占有できる。**直す案**: キー認証・上限のサイズ・同時実行の制限・前段のリバースプロキシ。

### 3. 「壁寸法」が、壁に分類される

`_classify_layers` は上から順の最初の一致で、「壁」が先に当たる(講義[第 3 回](../lecture/03-encoding-and-capstone.md))。

### 4. API の変換は、いつも**推論**の経路(CLI と挙動が違う)

`_run_pipeline` は、`parse_dxf` のあと、ルートを見ずに `generate_views` → `generate_mesh`(推論)へ進む。CLI の **ルート B(3D POLYFACE を直接)・ルート C(平面図の押し出し)は、API では使われない**。平面図を API に渡しても、押し出しにならない。**直す案**: CLI の分岐を共通の関数にして、API も同じ分岐を使う。

### 5. `.dwg` を受け付けるが、読めない

拡張子の確認は `.dwg` も通すが、`ezdxf` は DWG を読めない(`input_error` になる)。**直す案**: 受け付ける拡張子を `.dxf` だけにする。

### 6. その他の制約

- `cfg_min_snap`(50mm)が**モジュールの定数**で、設定から変えられない。
- `_decode_layer` は、化けた名前を**元に戻せないことがある**(そのまま返す)。
- API のジョブは**メモリ**(再起動で消える)。
- 時間切れは、**応答上のもの**(スレッドは止まらない)。
- 依存が重い(`open3d`・`torch`・`numba`)。`TripoSR/` は外部のコードで、このリポジトリのテスト対象外。
