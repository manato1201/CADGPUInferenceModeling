### Zバッファラスタライズ単体の高速化(boat.obj, 52,913頂点)
```
旧実装(numpy meshgridベクトル化):約4.1秒
新実装(numba njit):        約0.2秒（約20倍高速化）
```
ただし `mesh_to_dxf()` のtriview変換全体(boat.obj)では **改善が見られなかった**(52.9秒→48.6〜52.0秒)。プロファイルの結果、真のボトルネックは

- ezdxf書き出し(約39秒)

であることが判明した。これらはIMPROVEMENT_PLAN.md記載のPhase 4a/4bのスコープ外(ラスタライズ内ループのみが対象)。**Phase 4bのマルチビュー並列化は、この新事実を踏まえるとラスタライズ以外がボトルネックのため効果が薄いと判断し、実施を見送った。**

### 押し出し処理時間(2DDXF_Sample.dxf)
```
baseline.json(Phase 1時点): 114.98秒
Phase 3後(同条件で再計測):   119.38秒(誤差範囲)
Final Phase時点(再計測):      137.37秒
```
Phase 3(端点スナップのcKDTree化)によるO(N²)ループの解消は、本サンプル(壁線分156本・端点312個)では**支配的なコストではなかった**(スナップ処理自体は0.0025秒)。実測とプロファイルにより、押し出し処理の主要コストは開口部カット(`trimesh.boolean.difference`)であることが判明した。実行間の時間変動(約115〜137秒)はシステム負荷によるばらつきであり、出力メッシュ(verts=1098, faces=1932, bounds)は全計測で完全に一致している。

**IMPROVEMENT_PLAN.md記載の「期待効果合計: 処理時間 約60%短縮」は未達。** 実装したPhase 3/4aはいずれも計画時点の想定ボトルネック分析(Phase 0)通りには効かず、実際のボトルネックは開口部カットのブーリアン演算・エッジ可視性判定のPythonループ・ezdxf書き出しであることが本フェーズを通じて判明した。これらは既存フェーズのスコープ外のため未着手。**今後の性能改善作業の優先順位は、この実測結果に基づいて見直すべきである。**

## 確実に達成した改善
- **モデルの多重ロード解消**(Phase 2): API/CLIでのTripoSR/Zero123++再ロードを構造的に防止
- **Zバッファラスタライズの計算量削減**(Phase 4a): 大規模メッシュ(5万頂点超)で約20倍高速化(全体時間には別ボトルネックのため未反映)
- **端点スナップのアルゴリズム改善**(Phase 3): O(N²)→O(N log N)。1000線分超の大規模図面では効果が出る設計(未検証: 手元に該当規模のサンプルなし)
- **可視率の実測ベース改善**(Phase 5): 78%台→80.5%(zbuf_size 1024)
- **APIの障害耐性向上**(Phase 6): エラー分類・タイムアウト検出・ジョブストアのメモリリーク防止

## 2026-11 の改善(開口カット・可視判定・DXF 書き出し・推論後の整形)

上の「既知の未解決事項」の 1・2 を解消した。計測は同じ PC(RTX 3070)、`tests/bench.py` と `out/raw_mesh.obj`(77,891 頂点・155,738 面)。

| 対象 | 変更前 | 変更後 | 何をしたか |
|---|---|---|---|
| 押し出し(`2DDXF_Sample.dxf`) | 約 107〜137 秒 | **約 1.2 秒** | 開口のカットで、manifold3d を直接呼ぶ(下の「原因」) |
| 隠線の可視判定(3 ビュー、155,738 面) | 約 31 秒 | **約 1 秒** | 辺ごとの Python ループを、全辺まとめての numpy 計算に。結果は完全に一致 |
| シルエット抽出(3 ビュー) | 約 28 秒 | 約 17.5 秒 | shapely の多角形をベクトル演算で作る(和集合そのものは速くならない) |
| DXF 書き出し(70 万本の LINE) | 約 26 秒 | 約 2 秒 | LINE を ezdxf のエンティティにせず、保存のときに DXF の文字列として差し込む |
| **triview 全体**(同じメッシュ) | **約 82 秒** | **約 22 秒** | 上の合計。LINE・レイヤー・座標は一致、ezdxf の厳密な読み込みと audit も通る |

### 原因: 開口は「切られていなかった」
- 押し出しの 100 秒超は、`trimesh.boolean.difference` の **"manifold" エンジンが毎回失敗**し(trimesh 4.0.5 は、manifold3d 3.x で廃止された `Manifold.from_mesh` を呼ぶ)、開口 1 つごとに **Blender を起動**(約 1.2 秒 × 100 回)していたことだった。
- しかも Blender の戻り値は `Scene` で、`len(result.faces)` が例外になり、**結果は捨てられて壁がそのまま返っていた**。つまり、変更前の出力(1,098 頂点・1,932 面)は、**開口が一つも切られていないメッシュ**だった。上の「出力メッシュが全計測で完全に一致」は、そのためである。
- 今は、押し出しの面の向き(裏返し)をそろえたうえで manifold3d を直接呼ぶ。出力は 1,717 頂点・3,418 面になり、開口の分だけ体積が減る(`tests/test_boolean.py` で、体積が解析解と一致することと、Blender に戻らないことを守る)。
- `use_union=True` も、同じ理由で一度も働いていなかった。今は働き、サンプルでは閉じたメッシュ(水密)になる。

### 推論の出力の整形(GPU の推論は未計測)
- `core/postprocessor.py` の `clean_inference_mesh`(浮島の除去・穴埋め・任意の Taubin 平滑化)を、`TripoSRConfig(cleanup=True)` で推論の直後に入れた。`smooth_iterations` は既定 0(角が丸くなるため)。
- `core/mesh_metrics.py` に、品質の指標(Chamfer 距離・水密・連結成分・浮島・穴の縁・退化面)を追加した。人工の「ノイズ・浮島・穴」で、整形により指標が良くなることを `tests/test_mesh_cleanup.py` で確かめた。
- **TripoSR のモデル(約 1.7 GB)がこの PC に無く、実際の推論では確かめていない。** `mc_resolution`・`foreground_ratio` の調整も、同じ理由で未実施のまま。

### 気づいたが、変えていないこと
- `_edge_visibility_zbuffer` の許容誤差は、コメントでは「奥行きの範囲に対する割合」だが、実装は**横方向の範囲**(`h_max - h_min`)を使っている。可視率に直結するので、変えるなら可視率(`tests/test_accuracy.py`)で確かめてから。
- 手前向きの面だけでシルエットを作ると速くなるが、隣り合う三角形の数値の隙間が穴として残る(サンプルで穴が 18 → 126 に増えた)ため、採用しなかった。
