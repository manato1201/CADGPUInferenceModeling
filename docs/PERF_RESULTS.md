### Zバッファ可視率(car.dxf)
| 設定 | 可視率 | 処理時間(3ビュー) |
|---|---|---|
| zbuf_size=512(旧既定) | 79.1% | 約8.7〜10.1秒 |
| **zbuf_size=1024(新既定)** | **80.5%** | 約9.7〜9.8秒 |

READMEの旧記載値(78.0%)とは測定条件がやや異なるが、解像度を上げることで可視率が改善する方向性を実測で確認し、既定値を1024に変更した。

### Zバッファラスタライズ単体の高速化(boat.obj, 52,913頂点)
```
旧実装(numpy meshgridベクトル化):約4.1秒
新実装(numba njit):        約0.2秒（約20倍高速化）
```
ただし `mesh_to_dxf()` のtriview変換全体(boat.obj)では **改善が見られなかった**(52.9秒→48.6〜52.0秒)。プロファイルの結果、真のボトルネックは
- エッジ可視性判定(`_edge_visibility_zbuffer`、408,320本をPythonループで逐次処理、約30秒)
- ezdxf書き出し(約39秒)
- shapelyシルエット抽出(約19秒)

であることが判明した。これらはIMPROVEMENT_PLAN.md記載のPhase 4a/4bのスコープ外(ラスタライズ内ループのみが対象)。**Phase 4bのマルチビュー並列化は、この新事実を踏まえるとラスタライズ以外がボトルネックのため効果が薄いと判断し、実施を見送った。**

### 押し出し処理時間(2DDXF_Sample.dxf)
```
baseline.json(Phase 1時点): 114.98秒
Phase 3後(同条件で再計測):   119.38秒(誤差範囲)
Final Phase時点(再計測):      137.37秒
```
Phase 3(端点スナップのcKDTree化)によるO(N²)ループの解消は、本サンプル(壁線分156本・端点312個)では**支配的なコストではなかった**(スナップ処理自体は0.0025秒)。実測とプロファイルにより、押し出し処理の主要コストは開口部カット(`trimesh.boolean.difference`)であることが判明した。実行間の時間変動(約115〜137秒)はシステム負荷によるばらつきであり、出力メッシュ(verts=1098, faces=1932, bounds)は全計測で完全に一致している。

**IMPROVEMENT_PLAN.md記載の「期待効果合計: 処理時間 約60%短縮」は未達。** 実装したPhase 3/4aはいずれも計画時点の想定ボトルネック分析(Phase 0)通りには効かず、実際のボトルネックは開口部カットのブーリアン演算・エッジ可視性判定のPythonループ・ezdxf書き出しであることが本フェーズを通じて判明した。これらは既存フェーズのスコープ外のため未着手。**今後の性能改善作業の優先順位は、この実測結果に基づいて見直すべきである。**

## 確実に達成した改善
- **モデルの多重ロード解消**(Phase 2): API/CLIでのTripoSR/Zero123++再ロードを構造的に防止
- **Zバッファラスタライズの計算量削減**(Phase 4a): 大規模メッシュ(5万頂点超)で約20倍高速化(全体時間には別ボトルネックのため未反映)
- **端点スナップのアルゴリズム改善**(Phase 3): O(N²)→O(N log N)。1000線分超の大規模図面では効果が出る設計(未検証: 手元に該当規模のサンプルなし)
- **可視率の実測ベース改善**(Phase 5): 78%台→80.5%(zbuf_size 1024)
- **APIの障害耐性向上**(Phase 6): エラー分類・タイムアウト検出・ジョブストアのメモリリーク防止

## 既知の未解決事項(今後の課題)
1. 押し出し処理(`floor_plan_extruder.py`)の開口部カット(`trimesh.boolean.difference`)が2DDXF_Sample.dxfで100秒超を占める。ブーリアン演算バックエンド(manifold3d等)の見直しや、開口部ごとの並列化が次の高速化対象になりうる。
2. `mesh_to_dxf.py`の`_edge_visibility_zbuffer`(エッジごとのPythonループ)とezdxf書き出しが大規模メッシュ(5万頂点超)のtriview変換で支配的。numba化またはベクトル化の余地がある。
3. `mc_resolution`・`foreground_ratio`(TripoSR推論パラメータ)のチューニングは、GPU推論・モデルダウンロード(計約2.5GB)が必要なため本フェーズでは未実施。
4. `2DDXF_Sample.dxf`のレイヤー名がmojibake(文字化け)しており、`cli.py run`をコンソール出力リダイレクト環境(一部のWindows端末エミュレータ)で実行すると`rich`ライブラリのUnicodeEncodeErrorでクラッシュする(パイプライン自体の処理は正常。コンソール表示のみの問題)。DXFのレイヤー名エンコーディング処理(`core/parser.py`)の見直しが必要。
